MVP-2 progress
  M2.1 - Dynamic address lifecycle + DHT republishing (IMPLEMENTED)
    Motivating failure (real test, 2026-08-14):
      10.174.110.x -> 172.20.56.x -> stale DHT record -> No route to host
    Root cause: libp2p wildcard TCP listener reports new interface
      addresses but does not expire them when the OS drops the interface.
    Fix: node keeps current_addrs (listen addresses whose IP is still
      configured locally). OS interface scan every 5 s drops stale
      addresses; NewListenAddr/ExpiredListenAddr update the set; any
      change re-signs the record (fresh issued_at) and republishes
      immediately; 30 s periodic republish keeps TTL fresh. A failed
      scan is fail-safe (nothing dropped). Record format unchanged.
    Tests: 4 new unit tests + 1 new integration test
      (address_change_is_republished_and_discovered). Suite now:
      62 unit + 3 integration, all passing.
  M2.2 - Dynamic rediscovery of stale records (IMPLEMENTED)
    Peer-side counterpart of M2.1: on session loss the node re-dials
      the cached address once (2 s) while scheduling a DHT lookup
      (3 s, 1 s retries, <= 10 attempts). Dial failures invalidate the
      failed candidates; WrongPeerId invalidates the whole record. A
      verified record replaces the cache whenever its issued_at is not
      older (equal timestamps still re-dial, never dropped silently).
    Dials allocate fresh ephemeral source ports (PortUse::New): on
      Windows, listener-port reuse for outgoing dials collides with the
      live listener (WSAEADDRINUSE). A bootstrap_dialing guard prevents
      duplicate dials to the same address.
    Tests: 2 new unit tests + 1 new integration test
      (stale_cached_address_recovers_via_rediscovery). Suite now:
      66 unit + 4 integration, all passing.
  M2.3 - External address discovery + dial-back validation (IMPLEMENTED)
    The acceptor of an inbound connection captures the dialer's source
      IP and reports it over the authenticated session (new AEAD Control
      frame type 9; crypto design unchanged).
    The owner classifies the IP (loopback / local interface -> ignore;
      else external candidate (IP, own listen port)) and asks the
      reporter to dial it back. A full handshake validates the candidate,
      which is merged into the signed DHT record; dial failure or 30 s
      timeout rejects it (<= 3 attempts, 15 s per attempt; validated
      addresses re-validated every 300 s).
    Probes dial with an unknown transport Peer ID and a fresh source
      port, so they are never suppressed by existing connections or
      colliding with the listener. Only the requested prober's result
      is accepted.
    Tests: 12 new unit tests + 1 new integration test
      (external_address_discovery_validation_and_advertisement). The
      loopback test seam (NodeOptions::external_ips) stands in for a
      public IP — on Windows the loopback source is always seen as
      127.0.0.1. Suite now: 78 unit + 5 integration, all passing;
      clippy/fmt clean; aarch64-linux-android check clean.
  M2.4 - NAT traversal / hole punching (IMPLEMENTED)
    Mechanism (libp2p DCUtR 0.12 + circuit relay v2 0.18, libp2p 0.54.1):
      both peers reserve circuits through a relay server; a relayed
      connection carries the session while DCUtR exchanges observed
      address candidates (from identify) over it; both sides then
      simultaneously dial the observed candidate; if the NATs permit, a
      direct connection replaces the relayed one and a fresh JeanGrey
      session (ML-DSA + ML-KEM, no reuse across transports) runs over it.
    NodeOptions { relay, relay_server }; CLI --relay PEERID@addr and
      --relay-server. Relay client transport chained via OrTransport;
      listening on <relay>/p2p-circuit yields a circuit address advertised
      in the signed DHT record.
    Connection path tracked per peer (Disconnected/Connecting/Direct/
      Relayed/Traversing/Failed), surfaced in the peers listing and
      [nat]/[connect] logs. Direct addresses dialed before circuit
      addresses. DCUtR punches automatically on every relayed connection;
      bounded per-peer traversal attempts (max 3), then the relayed path
      stays.
    Tests: unit (path states, traversal budget) + 1 new integration test
      (nat_traversal_relayed_session_punch_and_round_trip): relay R at
      9261, A at 9262, B at 9263; A dials B via the circuit; DCUtR
      punches to direct; fresh session; message + authenticated ack.
      Runtime ~2 s. Two test-harness bugs fixed while getting it green:
      (1) the relayed path starves unless BOTH nodes stay polled (only-A
      polling misses the relay's handshake frames to B; the 30 s
      handshake timeout closes the circuit; A's pending dial dies with
      "unexpected end of file") — fixed with Node::next_event + a
      wait_for_pair select-poller; (2) on loopback the punch (~110 ms
      after the relayed connection) beats the ML-KEM/ML-DSA handshake,
      so the via-relay path observation runs concurrently with the
      session wait (path map re-checked after every event). Suite now:
      78 unit + 6 integration, all passing; clippy/fmt clean.
    Known limitations: punch succeeds only on NAT topologies permitting
      simultaneous dials (symmetric NATs fail -> M2.5 relay); Windows
      keeps fresh source ports for outbound dials (M2.2 WSAEADDRINUSE
      fix), reducing punch success on port-restricted cones (one side's
      punch can fail with os error 10048 while the other side's punch
      still establishes the direct connection); AutoNAT only reports
      reachability when other autonat-capable peers probe us.
  Not yet started: M2.5 relay fallback, M2.6 reconnection, M2.7
    hardening.
  Do NOT mark mailbox/IPFS/Flutter work complete.

What the release includes
  - persistent cryptographic identity (user + device model)
  - self-certifying device Peer IDs
  - Kademlia discovery over the LAN
  - direct P2P TCP transport
  - ML-DSA authentication (FIPS 204, ML-DSA-65)
  - fresh ML-KEM session establishment (FIPS 203, ML-KEM-768)
  - HKDF-SHA256 session-key derivation
  - ChaCha20-Poly1305 AEAD encrypted bidirectional messaging
  - message IDs, replay/duplicate protection
  - authenticated delivery acknowledgements
  - CLI: init / node / lookup / send / peers
  - Windows x86_64 binary, Android ARM64 (Termux) binary

Physical-device validation

  - Android ARM64 <-> Android ARM64 (Termux) over Wi-Fi
    bidirectional messages and acks
  - Full annotated logs: docs/testing.md

Known limitations (as released / MVP-2 progress)
  - NAT traversal - IMPLEMENTED (M2.4); relay fallback pending (M2.5):
    nodes behind NAT reach each other over a circuit-relay v2 path and
    DCUtR hole punching upgrades it to a direct connection when the NAT
    topology permits (cone/port-restricted-cone); symmetric NATs and
    Windows source-port constraints can still fail the punch. Without a
    successful punch, a relayed connection still carries the session,
    but only while the relay is reachable; no store-and-forward relay
    fallback yet.
  - Stale DHT addresses after Wi-Fi/network change - FIXED (M2.1 + M2.2):
    the publisher drops addresses whose IP is no longer local and
    republishes immediately (M2.1); the peer side invalidates failed
    cached addresses and rediscovers the fresh record via the DHT
    (M2.2).
  - No offline delivery; no store-and-forward queue.
  - Sending to your own Peer ID hangs awaiting an ack; a send timeout
    is planned (M2.7).
